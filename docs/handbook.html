Marketplace — multi-tenant commerce, with a schema that talks back

Two services split by an SQS FIFO queue: a deterministic engine that owns all state and enforces tenant isolation, and a conversational layer that turns a chat into a validated schema-change proposal. Nothing an agent proposes ever applies itself.

NestJS ×2 + Next.js engine :3000 agents :3001 web :3002 Swagger /api/v1/docs DynamoDB · SQS · Redis · Cognito
What it is

Two services, one queue

MarketplaceEngine

The deterministic core: CRUD, tenant isolation, and an enforcing per-tenant dynamic schema registry. Owns every table. Also runs the SQS consumer that turns AI-proposed flows into records.

MarketplaceAgents

The conversational layer: an authenticated WebSocket gateway backed by a LangGraph.js state machine that turns a chat into a validated schema-change proposal and pushes it onto the queue. It owns no database.

Flow 1 of 5

How a request becomes a tenant

Authorization: Bearer <Cognito ID token>
      │
      ├─ packages/auth verifies signature, issuer, audience, expiry
      ├─ claims.ts extracts custom:tenant_id and validates its shape
      │      an id that fails the pattern is rejected here, once
      │
      └─ DynamoRepository builds every partition key from that claim
             its methods take no tenant argument at all

The tenant comes only from the token claim, and DynamoRepository is the only code that builds a partition key. A cross-tenant query is therefore not something you are forbidden to write — it is something you cannot write.

Cross-tenant reads return 404, never 403. A 403 confirms the resource exists. Asked for another tenant's product by exact id, the engine answers as if it does not exist, because for that caller it does not.

Role selects which navigation the console shows and nothing more. It is not an authorization boundary — the engine enforces tenant isolation on every route and enforces nothing about role, so an admin URL typed by hand works fine for a buyer.

Flow 2 of 5

A chat becomes a schema change

This is the flow the whole architecture exists for, and every step of it is a place where an AI could have been allowed to write to a database and deliberately was not.

browser ──WS /agents (socket.io, auth.token = Cognito ID token)──► apps/agents
   thread.start │ thread.resume │ message │ confirm │ reject
   ◄── state snapshots, error problem documents ──

   confirm
      └─► SQS FIFO  { type: PROPOSE_FLOW, ... }   MessageGroupId = tenantId
                │
apps/engine/src/messaging (SQS consumer)
                ├─ re-validate tenantId against the same pattern claims.ts enforces
                ├─ parse against the contract schema
                ├─ dedupe on messageId in Redis
                └─ write Flow { status: 'proposed' }        ← and nothing more

human ──► POST /api/v1/flows/:id/execute
             └─ applies the diff, raises the registry version (idempotent)

Why the consumer re-validates what the gateway already checked

The consumer is a second, unauthenticated entry point for a tenant id. Unlike every HTTP route, there is no JWT behind it. So it re-validates the tenant id against the same pattern the auth chokepoint enforces, before that value ever reaches a DynamoDB key.

What happens to a bad message

  • Invalid tenant, failed schema parse, or malformed JSON: the message is left unacknowledged rather than deleted, so the redrive policy (maxReceiveCount: 5) moves it to the DLQ for forensics instead of discarding it silently.
  • The queue is FIFO with MessageGroupId set to the tenant id, so a poison message head-of-line-blocks that tenant's queue for up to five receive attempts and then clears. Other tenants' groups are unaffected.
  • Redelivery is deduplicated per messageId in Redis, so a retried message never creates a second Flow.

Add-only, on purpose

There is no backfill, so field removal and type changes are rejected. Attributes added by a Flow are absent from records written earlier, and POST /products/search will not match those records. Executing a flow raises the registry version; the console re-reads it, so a field an agent proposed appears everywhere it belongs with no page reload and no line of UI code naming it.

Flow 3 of 5

Cart, checkout, order, and the pipeline

GET  /cart                       the caller's open cart
PUT  /cart/lines/:productId      set a line quantity
POST /checkout                   turn the cart into an order
POST /orders   (Idempotency-Key required)
       └─ TransactWriteItems: lock unit prices + decrement stock under
          condition expressions — never read-then-write in app code
POST /orders/:id/pay
POST /orders/:id/advance         move it to the next configured stage
POST /orders/:id/cancel
GET  /settings/pipeline · PUT /settings/pipeline    the stage list itself

Idempotency is required, not optional

Clients and load balancers retry, and neither double-charging nor double-booking is acceptable. The same key twice, same tenant and user, returns the stored response from the first request. The same key again while the first is still in flight returns 409 request-in-progress. Keys are scoped idem:<tenantId>:<userId>:<key>, so two users cannot collide on a key one of them chose and read each other's response.

Bookings take the same shape

POST /bookings enforces event capacity through the same transactional condition-expression mechanism. Losers of a race get 409, never a corrupted counter.

Order threads — the messages between buyer and seller about one order — hang off POST /orders/:id/messages and GET /orders/:id/messages, and the agents service can read a thread at GET /threads/:id.

Flow 4 of 5

Product images

  1. The browser posts the file to the engine

    POST /api/v1/uploads/product-image, multipart file.

  2. The engine checks size and magic number

    A declared image/png that is really an HTML document is refused. Content type from the client is not evidence.

  3. It is written to the marketplace-media bucket

    Stored objects are public-read by design, so an <img> loads one with no credentials and no signing round-trip.

Tenant isolation does not extend to an image URL. That is the deliberate trade for credential-free <img> loads. Do not put anything in that bucket you would not publish.

Images can only be set when a product is created, because the engine has no update route for them.

Flow 5 of 5

Storefront and onboarding

A tenant's public face is edited as a draft and published atomically.

GET /storefront            the live storefront
GET /storefront/draft      the working copy
PUT /storefront/draft      edit it
POST /storefront/publish   promote draft → live
POST /storefront/banner-art        generated banner
GET/PUT /storefront/onboarding     the setup checklist state
GET/PUT /settings/announcement     the site-wide banner message

The agents service assists here too: POST /copywriter/draft writes product copy, POST /setup-plan/apply turns a plan into storefront settings, and POST /support/ask answers a buyer's question against the tenant's own data.

Interface

API reference

Every route is under /api/v1 and requires a Cognito ID token except /health/live and /health/ready. List endpoints take ?limit= (1–100, default 25) and ?cursor= (an opaque base64 LastEvaluatedKey) and return { items, nextCursor }.

Swagger

Wired by packages/openapi/src/setup.ts, mounted only when DOCS_ENABLED is true, after setGlobalPrefix('api/v1') and before listen:

  • UI at :3000/api/v1/docs (engine) and :3001/api/v1/docs (agents); JSON at /api/v1/docs-json.
  • A global bearer security requirement. A route marked @Public() emits an empty operation-level security array, which OpenAPI 3 treats as a full override — never a merge.
  • Every operation gains a default response of application/problem+json (RFC 9457), and every non-public one also gains 401.
  • "Try it out" works without a copy-paste. A small customJsStr waits for window.ui, calls the gated POST ../dev/token on the same origin, and pre-authorizes the result. Failure — flag off, Cognito down, dev-token package absent — is non-fatal by construction: it logs and leaves the Authorize button working normally.
  • persistAuthorization is on, so a reload keeps you signed in.
helmet's contentSecurityPolicy is deliberately off in app.factory.ts. The only HTML this service serves is the Swagger UI, which helmet's default policy breaks — it loads its own inline bundle. The CSP that matters belongs on the console, which is what actually renders documents.

Guarantees

Five invariants, asserted end to end

These are not unit tests. They run against the full Docker stack.

  1. Tenant isolation

    A request for another tenant's resource by exact id returns 404 — never 403, never the resource.

  2. No oversell (capacity)

    Concurrent bookings against a capacity-limited event never exceed capacity; losers get 409, not a corrupted counter.

  3. No oversell (stock)

    The same guarantee for concurrent orders against limited product stock.

  4. Idempotency

    The same key twice produces exactly one order (or booking) and one stock decrement, never two.

  5. Flow lifecycle

    A proposed Flow never mutates the registry until a human executes it, and executing it is itself idempotent — re-executing an applied Flow does not bump the version again.

Money is integer minor units plus an ISO-4217 currency. Never floats, anywhere.

Operations

Running it

pnpm install
pnpm --filter @marketplace/web exec playwright install chromium   # one-time
pnpm docker:up      # dynamodb-local, localstack (sqs + s3), redis, cognito-local,
                    # seed, engine, ollama, ollama-init, agents, web
pnpm test           # unit + integration
pnpm e2e            # engine, then agents, then web — then tears down
pnpm docker:down

docker:up runs the seed container first: it creates the DynamoDB table, the FIFO queue and its DLQ, and a Cognito user pool, then writes the generated identifiers to docker/.env.generated, which both services read.

The first docker:up on a fresh machine takes minutes. ollama-init pulls qwen2.5:7b-instruct — 4.7 GB. Subsequent runs reuse the ollama-models volume and start in seconds. docker:down and the e2e teardown never run docker compose down -v: that would delete the volume and force a re-download. They do wipe everything else, including the Cognito pool, so each run still starts from a clean data plane.

Or via the devkit, which is what the rest of this machine uses:

powershell -File $dk\marketplace\devup.ps1 -CheckOnly -Test

Marketplace owns the base defaults on this machine — 3000-3002, 4566, 6379, 8000, 9229, 11435. Every other project moved off them. See _devkit/PORTMAP.md.
